# Check 40: the mod without a screen

**Answer:** Yes, with four changes — the validator lists a mod split into files, `claude plugin test` runs with no sign-in, a mod command's answer is kept with no model turn, the timer keeps firing between turns, and a `{ drop }` keeps a `claude -p` prompt out of the model and the transcript. The changes: a classic hook never sees a mod command's typed line; the release CI pins (2.1.278) can't run `claude plugin test` without a variable and lists nothing for the repository root; and a mod's own `prompt.submit` hook doesn't see the prompt its own timer submits.

## Question

What a mod can do with no screen, which the rest of the mod relies on: how the validator reports a mod split into files; whether its tests run without a sign-in; how a mod command meets the command hooks; whether a mod's timer and its submitted prompts keep working across turns; and whether messages from other sessions can be kept out of a session's conversation.

(The last part, `session.receive` seeing a message from another session, can't be asked here: check 27 found no route by which a script sends a message into a running session, so check 41 asks it in Desktop.)

## Tested on

macOS 27.0.1, Claude Code 2.1.302 (headless `claude -p`, started from a terminal shell; Claude Desktop not used), 19 October 2026. The validator and the test command were also run on 2.1.278 (the release CI pins) and, for a table, on 2.1.280, 2.1.284, 2.1.288, 2.1.292, 2.1.295, 2.1.296, 2.1.299 and 2.1.302, each fetched with `npx`. No Windows run. 2.1.295, the release Task 2 later pinned in CI, was added on 19 October 2026 after Task 2 (see the 2.1.295 item under Evidence).

## Method

**What the documentation says (read on 19 October 2026).** The mod reference that ships with Claude Code (the `plugin-authoring` skill's `reference.md` and `types/claude-code.d.ts`; the copy on disk was the one Claude Code 2.1.299 unpacked into a temporary folder when the skill loaded):

- `$.clock.every(ms, fn)` "calls `fn` every `ms` milliseconds (at least 1) until `cancel()`". The reference says timers "run until cancelled or until the module reloads" and that work meant to outlive a dispatch starts from a `session.start` hook, "which fires once when the session is ready and is awaited before the first prompt".
- `$.prompt.submit` "queues a prompt that starts a turn of its own once the session is idle (never folded into a running turn; the call resolves as that turn starts, not when it ends), so background work can wake a quiet session". The types say it "goes through every hook but the calling one (the plugin's others see it)", with origin `{ kind: 'plugin', name }`, and the model reads it as "The <name> plugin sent a message: ...".
- `prompt.submit`'s `{ drop: reason }` means "the prompt did not enter"; the hook's text is shown to the user as the reason. Origin `sdk` is "the SDK host's own turn (`claude -p`, the Agent SDK), not typed at a terminal".
- `session.receive`'s `{ consumed: reason }` "takes the delivery, answered without `next`: it is not queued, not written to the transcript and never reaches the model". Its origins include `peer`, `bridge` and `task-notification`.
- `command.run`: a hook's own answer without `next` "runs no command: its `text` is shown as the command's output", under the names of the plugins hooking the command; `exitCode` is what a headless `claude -p "/lint"` exits with. The reference says `claude plugin validate` reports what the module hooks and calls, a `command.run` hook that answers its own command on a line `answers its own command:`, and `gatingHooks` in the JSON report.
- `claude plugin test <folder>` "runs the plugin's `*.test.ts` files against the engine itself". Neither file says anything about a sign-in.

**The probe** (`probes/40-mod-headless/`): a plugin with a mod in two files and a classic hook beside it, all in one `hooks/hooks.json` (`modules` and `hooks`).

- `register.ts` imports `part.ts`. It registers a command `digest` answering `{ text: 'probe digest' }`; at `session.start` it starts `$.clock.every(5000, …)`, logging each fire, and on the third calls `$.prompt.submit({ text: 'probe: timer prompt' })`, logging the call and when it resolves; and it has two `ui.render` hooks that only pass on, so the validator shows how it spells their matchers.
- `part.ts` holds one hook: `prompt.submit`, which logs every prompt with its origin and answers `{ drop: 'probe' }` for a text beginning `probe-drop:`. It makes a call (`$.clock.now`) that `register.ts` doesn't.
- `hooks/log-prompt.js` is the classic UserPromptSubmit hook: it logs the prompt it receives.

`run.js` makes everything in throwaway folders under the temporary folder, loading a scratch copy of the probe with a small test file added to the copy only (the repository's own `claude plugin test .` would otherwise find it under `probes/`). Every session used `--setting-sources project` and a clean environment (none of the calling session's variables), and no `--model`, so the default one answered.

1. `claude plugin validate --json` on the scratch copy, and on the repository root (the real first-piece mod).
2. `claude plugin test` on the copy with `HOME` set to an empty folder, after `claude auth status` there, which says `loggedIn: false`.
3. `claude -p "/digest" --output-format stream-json --verbose`.
4. Two long-lived `claude -p --input-format stream-json --output-format stream-json --verbose` sessions (the route check 27 found works), each left open for 30 seconds after the timer's prompt:
   - **A (idle):** one ordinary message ("Reply with the single word: ok."), then `probe-drop: sent while idle`, with the timer's third fire coming after.
   - **B (running):** the same ordinary message, then, just after the timer's second fire, a long turn ("Write a story of about 800 words…", no tools), then `probe-drop: sent while a turn runs` three seconds into it, so the timer's third fire (15 seconds in) found the turn running.
5. The same validate and test runs, the help text and a table of releases, on 2.1.278 and the releases between, with `npx`.

The reports worth keeping are in `probes/40-mod-headless/reports/` with the home folder replaced by `<home>`, the repository by `<repo>` and scratch folders by `<scratch>`: `validate-probe.json`, `validate-repo.json`, `validate-repo-plugin-json.json` (the repository's plugin manifest as the target), their `-2.1.278` counterparts, `validate-repo-<version>.json` for 2.1.278 to 2.1.302 (2.1.295 included), `plugin-test.txt`, `plugin-test-2.1.278.txt`, `ci-2.1.278-help.txt`, `ci-versions.txt` and `sessions.json` (the events and logs of runs 3 and 4). Afterwards `run.js` listed and removed the three folders the sessions made under `~/.claude/projects/` (matched by the scratch projects' names) and the scratch folders. The npx cache now holds the Claude Code releases fetched (2.1.278 to 2.1.302), and the probe's own log folder holds its raw logs; nothing else on the computer changed.

## What it means for the design

For Tasks 2, 6, 9 and 11:

1. **A mod in several files validates, with its hooks and calls listed under the entry file.** The brief's two-file split holds (`register.ts` importing `part.ts`). No fall-back: the mod needn't be one file (`hooks/register.tsx`). Task 2's checks read the entry file's notes (`./register.ts hooks: …`, `./register.ts calls: …`), with an imported file's hook and calls folded in, so they can't say which file made a call; a call in a helper function carries `(via <function>)`. The spellings: `command.run{command=NAME}`, `ui.render{component=Pane, requestId=ID}`, `ui.render{component=AbovePrompt}`. Task 2 builds its fixtures from `reports/validate-probe.json` and `reports/validate-repo.json`.
2. **`claude plugin test` runs with no sign-in on 2.1.302.** No fall-back on this Mac: `npm run mod-check` needs no sign-in. On the release CI pins it needs more. On **2.1.278** the command is absent and says `unknown command 'test'` unless `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1` is set; with it set it runs, still with no sign-in (found with an empty `HOME` standing in for CI, not in CI itself). So CI's `validate` job either sets that variable for the test step, or moves its pin to 2.1.288 or later; until then the mod's tests also run on the Mac before every push, said in each pull request. Moving the pin is the build session's call.
3. **`scripts/mod/validate.js` points at the repository root, and on 2.1.278 that reads no hooks.** The report for the root holds no `contents` on 2.1.278 (to 2.1.288), so the script would say the mod hooks nothing. Pointing it at `.claude-plugin/plugin.json` gives the hooks and calls on 2.1.278 and 2.1.302 alike (`reports/validate-repo-plugin-json*.json`). Task 2 changes the target (or moves the pin to 2.1.292 or later, which was enough for the first piece alone but not once the mod passes `$` across an import: see the 2.1.295 item under Evidence); its fixtures use both report shapes. Its regular expressions need no change: they read only the `hooks:` and `calls:` notes, which 2.1.278 spells the same way (it has no `answers its own command` or `gatingHooks`).
4. **A classic UserPromptSubmit hook doesn't see a mod command's typed line.** `/digest`, answered by the mod's `command.run` hook, never reached the classic hook, nor the mod's own `prompt.submit` hook. (Check 32 found a hook sees a plugin's markdown command, which starts a turn; a mod command answers before that.) Task 6's change to the board-context hook still stands, harmless: the hook just never has a mod command's line to answer.
5. **A mod command's `{ text }` answer is kept with no model turn.** `claude -p "/digest"` printed the text, with the plugin's name in front, at no cost and in no turn. No fall-back: `/digest` shows the command's output, and the briefing does not need to open in the pane's own view (Task 11).
6. **`$.clock.every` keeps firing between turns in a long-lived session**, from the session's start, every 5.0 seconds with no drift, through idle and through a running turn. No fall-back: Shape 2 keeps the mod's timer (build loop, Task 6) and Task 7's Shape 2 half is built; the plugin monitor of check 26 isn't needed for it. The courier's half is still decided in Desktop by check 41.
7. **`$.prompt.submit` from the timer starts a turn at once when idle and waits behind a running one**, resolving as its own turn starts. It is never folded into the running turn, so a timer prompt can't interrupt work. Its origin is the plugin's, which the model reads as `The <plugin> plugin sent a message:`. **The mod's own `prompt.submit` hook (`part.ts`'s, another file of the same mod) didn't see it**, so a mod can't drop or rewrite its own submitted prompt; the classic hook does see it. This differs from the documentation, which says the plugin's other hooks see a prompt a plugin submits (quoted under Method). The probe found otherwise, and the debug line that explained it (re-entry, as above) was not kept, so the reason rests on one unkept line. Treat the documentation's sentence as not holding for a hook in the same mod.
8. **A prompt sent into a `stream-json` session arrives with origin `sdk`**, and a `prompt.submit` hook's `{ drop }` keeps it from the model and from the transcript: no model turn, no user row, a `result` event with `num_turns` 0 and the text `Prompt dropped by a hook: <reason>`. No fall-back: Task 11's Wheelhouse traffic can be told apart by origin and dropped. In this trial, a drop sent while a turn (with no tool call) ran waited until the turn ended before the hook ran.
9. **Not asked here:** whether `session.receive` sees a message from another session, and whether its `{ consumed }` keeps it out of the conversation. Check 41 asks it in Desktop.
