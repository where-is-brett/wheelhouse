# Check 39: what the transcripts show about a message and a turn

**Answer:** Yes, with two gaps — in the director's Desktop sessions a typed message is marked `origin.kind: "human"`, and another session's message (`peer`), a task notification, a hook's added context, a tool result (an `AskUserQuestion` answer among them) and a meta entry each carry their own field; every assistant entry gives its turn's input, cache read and cache creation tokens and the model; every message entry carries `cwd` and `sessionId`, and a subagent's file sits under its parent session and carries the parent's id. The gaps: no message sent from the phone was found or made, so how one is marked is unseen (the mod's own types name a separate `bridge` origin); and a message sent by `claude -p --resume`, the watcher's route, looks exactly like the SDK host's own message, so in a headless session only its text (`Wheelhouse:`) tells it apart.

## Question

From Claude Code's transcript files (`~/.claude/projects/*/*.jsonl` and their subagent files), whether a reader can tell a message the director typed or sent from the phone from one relayed by another session, a hook's added context, a task notification or a card answer; whether each assistant entry gives the context size of its turn (input, cache read and cache creation tokens) and the model; and whether entries carry `cwd` and the session id, so a session can be matched to a project and to its part (front desk, foreman, feature). Task 7 builds its counts on the answer.

## Tested on

19 October 2026, on macOS with Claude Code 2.1.302, headless (`claude -p` started from a shell inside a Claude Code session, with that session's variables left out, as check 27 did), the default model. The director's own transcripts were read on the same Mac: every session changed in the last 7 days, written by Claude Code 2.1.111 to 2.1.302, all from Desktop. No Windows run, no phone.

Documentation read the same day:

- https://code.claude.com/docs/en/claude-directory (`<session>/subagents/`, `<session>/tool-results/`, set-aside transcripts)
- https://code.claude.com/docs/en/hooks (`transcript_path`, `agent_transcript_path` in a nested `subagents/` folder, `additionalContext` wrapped as a system reminder and saved in the transcript, the file written asynchronously)
- https://code.claude.com/docs/en/headless (`--permission-prompts`, `AskUserQuestion` removed when nobody can answer, `--resume` from a script)
- https://code.claude.com/docs/en/tools-reference (`AskUserQuestion`)

These are the mod's names, not the transcript's.

## Method

**The probe,** `probes/39-transcripts/run.js`, two modes.

1. **The scratch run** (`node probes/39-transcripts/run.js`). A throwaway git project under the temporary folder, with one project hook (`hooks/context.js`) adding a line of context at SessionStart and at UserPromptSubmit. One `claude -p --input-format stream-json --output-format stream-json --permission-prompt-tool stdio --setting-sources project` session, held open as the stand-in for the director's session, is sent, one at a time:
   - a plain message ("Reply with the single word: ok.");
   - a request to ask one `AskUserQuestion` with the options "Approve" and "Not now". The script is the permission host (as the Agent SDK's `canUseTool` is): it answers the `can_use_tool` request with `allow` and `answers` set to "Approve", a click on the card's option;
   - a request to start one background subagent, whose end comes back as a task notification and a turn of its own;
   - a reply code typed as a message, "K7QD Approve" (the design's reply codes, section 17.1).

   Then a second process relays one message into the same session by the watcher's route (`scripts/watcher/waker.js`, from check 27): `claude -p "Wheelhouse: read relay.md" --resume <session id>`. Check 27 found no route by which a script sends a message into a running Desktop session, so this is the nearest real relay that can be driven headless; Desktop's own relays between sessions are read from the director's transcripts instead (item 2). The run then reads the session's transcript and its subagent files and lists every entry: its type, its fields, and any marker of where it came from. It cost five turns and one relayed turn (about 30,000 tokens read from cache per turn). A copy of its report, with ids, folders and model names masked, is `probes/39-transcripts/reports/scratch.txt` (written again with `--reread`, which reads the last run's kept transcript with no new session).

   A first attempt without a permission host could not ask: `AskUserQuestion` was not offered to the model at all in a plain `claude -p` run (the documentation says tools that need a person are removed when nobody can answer). With `--permission-prompt-tool stdio` and the script answering, it was asked and answered.
2. **The `--mine` pass** (`node probes/39-transcripts/run.js --mine`), ruling E2. It reads every session file under `~/.claude/projects/` changed in the last 7 days, with its `subagents/` files and their `.meta.json`, leaving out the throwaway folders probes make, and prints only entry types, field names, kinds of marker and counts. A guard decides what may be printed: a key is shown only when it is a plain field name not shaped like an id (an API id such as `toolu_…`, a UUID, a long hex string, a run of three digits), and every child of a map keyed by ids or by the person's own data (`wireToolInputs`, `modelUsage`, `answers`, file backups and the like, or any object with over 40 keys) is shown as `<key>`; a tool's input and result are shown one level down through a short list of known fields; a value is shown only for a fixed list of fields and only when it is a short kind word (or, for `version`, a version number); an MCP tool's name is shown as `mcp tool`; a leading tag is named only when it is one of the known markers, and counted as "other tag" otherwise. `tests/probes/39-transcripts/run.test.js` feeds it a hostile transcript and checks that none of its ids or words come out. (A first version of the guard let tool-use ids through as key paths; that output was deleted and the pass run again with this guard.) It never prints message text, `cwd`, paths, session ids, model names, project or folder names. Its output went to the session's scratch folder, outside the repository, and is not kept. This note quotes only field names, kinds of marker and counts from it.

## Evidence

**The director's transcripts, last 7 days:** 121 session files and 762 subagent files, about 204,000 entries (the figures here are from one pass; the sessions still running kept writing between passes), all from Desktop (`entrypoint: "claude-desktop"`). No line failed to parse, no file ended without a newline, no entry lacked a `type`. The scratch session's 121 entries were the same. (The documentation warns the file is written asynchronously, so a reader may meet a last line still being written; none was seen.)

**1. Telling the kinds of message apart.** On recent releases a user prompt carries `promptSource` and `turnOrigin`, and most carry `origin.kind` naming the sender (slash commands and compaction summaries carry none of them; see Versions below). A message that arrives while a turn is running is kept as an attachment, `attachment.type: "queued_command"`, with `attachment.origin.kind` and the text in `attachment.prompt`, not as a user entry.

Other user prompts in the director's files: slash commands (`<command-name>`, `<command-message>`, `<local-command-stdout>`, no `origin`), `[Request interrupted by user`, one `origin.kind: "plugin"`, and in subagent files the task given by the main session (`origin.kind: "coordinator"`, `isMeta: true`).

**Versions.** `origin` is a recent field. In the director's files, prompts from Claude Code 2.1.111 to 2.1.170 have no `origin` (`promptSource` appears in 2.1.170, where 20 plain prompts are `promptSource: "sdk"` with no `origin`); `origin.kind: "human"` appears from 2.1.197 on. On 2.1.299, the release with most prompts this week (622), the prompts without `origin` were slash commands and their output, compaction summaries, `[Request interrupted by user`, and `promptSource: "sdk"` prompts starting `<system-reminder>` or `<ci-monitor-event>` or opening a session. The 37 prompts written by 2.1.302 (today) are all `promptSource: "sdk"` first prompts of sessions, with no typed message among them yet.

**2. A turn's context and the model.** Every assistant entry (68,620 in the director's files, 13 in the scratch run) has `message.usage.input_tokens`, `message.usage.cache_read_input_tokens`, `message.usage.cache_creation_input_tokens` (with `message.usage.cache_creation.ephemeral_5m_input_tokens` and `ephemeral_1h_input_tokens`), `message.usage.output_tokens`, and `message.model`; `requestId` on all but a few. One API response is written as one entry per content block (thinking, text, tool use), all sharing `message.id`: 58,580 entries share an id with another, and on every one of them the three input figures were the same; only `output_tokens` may differ. 66 entries have the model `<synthetic>` (made by Claude Code, not the API). About half also carry `message.usage.iterations[]`. Session files also hold `cost-state` entries with running totals per model (`modelUsage.<model>.inputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`).

**3. `cwd`, the session id and subagents.** `sessionId` is on every entry except `file-history-snapshot` and `file-history-delta`; `cwd` is on every `user`, `assistant`, `attachment` and `system` entry, and on none of the bookkeeping entries (`queue-operation`, `last-prompt`, `custom-title`, `agent-name`, `bridge-session`, `api-request`, `cost-state` and so on). A subagent's transcript is `<project>/<session id>/subagents/agent-<agent id>.jsonl`: all 119,718 of its entries carry the parent's `sessionId` and an `agentId` equal to the file's own id, all but four (`api-request` bookkeeping) `isSidechain: true`, and each file's first entry `parentUuid: null`. Beside it, `agent-<agent id>.meta.json` holds `agentType`, `description`, `toolUseId`, `spawnDepth` and, for a subagent started by a subagent, `parentAgentId`; 697 of the 714 `toolUseId`s were found as an Agent tool call's id in the parent session file (the rest were started by subagents). Subagent entries are not in the session file.

**4. Desktop and `claude -p`.** The same field names and markers. Every entry type the scratch run wrote also appears in the director's Desktop files; Desktop adds more (`bridge-session`, `custom-title`, `agent-name`, `pr-link`, `file-history-snapshot`, `attachment:queued_command`, `system:compact_boundary` and others). The values differ: `entrypoint` is `sdk-cli` headless and `claude-desktop` in Desktop, and a headless message is `promptSource: "sdk"`, `turnOrigin: "sdk"` with no `origin`, where a Desktop message typed by the director is `origin.kind: "human"`.

**5. Malformed or partial lines.** None in about 204,000 entries or in the scratch run.

## What it means for the design

For Task 7:

1. **The director's own messages** are the user entries in the front desk's session file (not its `subagents/` files) with `origin.kind` `"human"`, plus the `queued_command` attachments with `attachment.origin.kind` `"human"`, counted once each. Count `"bridge"` the same way, in case a phone message is stamped so; if it is stamped `"human"`, it is counted already. Leave out tool results, `isMeta` entries and `isCompactSummary` entries. A text stamped `human` is counted even when it starts with a block Desktop adds (`<system-reminder>`, `<pasted_content>`). An entry that is not stamped `human` or `bridge` is never counted, whatever its text, so `Wheelhouse:`, `<task-notification>` and `<side-sessions-event` texts stay out; Task 7's tests pin both. A reply code ("K7QD Approve") is the director's message and is counted.
2. **Entries without `origin`** (Claude Code before 2.1.197) fall back to the plan's rule: count prompts with none of the known prefixes, and say the count may include a few that aren't the director's. The front desk will run on 2.1.299 or later (check 40), where this doesn't arise.
3. **A turn's context** is `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` from `message.usage` of the assistant entries, taken once per `message.id` (the three are the same on each of its entries), skipping the model `<synthetic>`; the turn's figure is the last API response before the next prompt. The model is `message.model`. The context gauge's own record (safety plan, Task 11) is not needed for this; it stays the cross-check.
4. **Matching a session to its project and part:** `cwd` on any message entry gives the folder, so the main checkout (front desk, foreman) or a worktree under `.claude/worktrees/` (a feature); `sessionId` and the file name give the session. Front desk and foreman share the main checkout; the foreman's first prompt starts `Wheelhouse foreman:`, and the watcher keeps the ids of the sessions it starts. Subagent files are found under `<session id>/subagents/` and belong to that session.
5. **The format is internal and changes between releases** (the documentation says so, and `origin` arrived within the releases read here). Task 7's reader skips entry types it doesn't know, never fails on an unknown field, and its tests pin the fields above with a small fixture.
6. **Headless sessions** (foreman, feature) can't tell the watcher's relay from their own first prompt by fields; their messages are not the director's anyway, so Task 7 doesn't count them.
