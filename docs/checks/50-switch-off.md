# Check 50: switching a project's own parts off and on

**Answer:** Deferred — the probe is written and its dry run passes, but the live run on the Mac waits on the director's card before Part 1 of the install plan, and Windows on Card 2. Below is what the documentation leads us to expect for each question, marked as untried; none of it has been seen.

## Question

From a project's git-ignored local settings (`.claude/settings.local.json`), how to keep a skill, an agent, a slash command and a hook that the project's committed folders define out of every session on this computer (and, from the committed settings, a personal skill in `~/.claude/skills/`), and put them back, without deleting or moving a file: whether a `Skill(<name>)` or `Agent(<name>)` deny rule does it (and whether the director typing `/<name>` is refused too), or another documented setting does it better; whether a local `enabledPlugins` entry set `false` beats the project's `true`, and a local `sandbox.enabled: false` beats the project's `true`; when a project agent and a plugin agent share a name, which one a dispatch by the bare name reaches; whether an untracked skill folder listed in `.git/info/exclude` loads; whether a change takes effect at the next session start with no restart; and whether a session's `init` event lists its skills, agents and plugins before any model call.

The answers feed Tasks 3, 5 and 7 of the install plan (`docs/superpowers/plans/2026-10-19-wheelhouse-install.md`): `route` for each kind (`skill`, `agent`, `command`, `hook`), whether a typed `/<name>` is refused, `pluginOff`, `sandboxOff`, `sameName`, `untrackedLoads` and `initBeforeModel`.

## Method

`node probes/50-switch-off/run.js --go`, modelled on check 24's probe (`probes/24-pinning/run.js`). Without `--go` it only prints its plan.

- **Copies first.** It copies `~/.claude/plugins/known_marketplaces.json`, `~/.claude/plugins/installed_plugins.json`, `~/.claude/settings.json`, `~/.claude.json` and git's global ignore file (Claude Code adds its local settings file there the first time it writes one) to a new folder under the temporary folder, and refuses to start if its marketplace, its cache folder or its personal skill is already there.
- **The scratch parts**, all under one new folder in the temporary folder, with made-up names: a project (a git repository) with one committed skill (`probe-skill`), one agent named `builder`, one command (`probe-command`) and one `SessionStart` hook in its committed `.claude/` folders, and one untracked skill folder listed in `.git/info/exclude`; a plugin (its own git repository) with its own agent `builder` and its own `SessionStart` hook; and a marketplace listing the plugin as a `url` source with a `file://` address, `ref` and `sha`, as check 30 did, so nothing needs GitHub. It also writes one personal skill, `~/.claude/skills/wheelhouse-probe-50-personal/`. Each part, when it runs, writes a marker file into the project's `ran/` folder, so what ran is read from the files, not from what Claude says.
- **Install.** `claude plugin marketplace add <folder> --scope project` and `claude plugin install wheelhouse-probe-tools@wheelhouse-probe-switch --scope project` in the project, then a commit of what that wrote and a git worktree of the project.
- **Each candidate route,** with the terminal's Claude Code and with the Desktop app's copy: the probe writes the route into the project's `.claude/settings.local.json` (or, for the personal skill and the sandbox, into the committed settings), starts `claude -p --input-format stream-json --output-format stream-json --verbose` in the project without sending anything, reads the `init` event (its `skills`, `agents`, `slash_commands` and `plugins`) and the hook markers, and stops the session there. Then, as the trial needs, it runs one turn asking Claude to use `probe-skill`, the personal skill and `probe-command` and to dispatch `builder` and `wheelhouse-probe-tools:builder`; one turn whose prompt is `/probe-skill`, `/probe-command` or the personal skill's `/<name>`, as the director would type it; or one Bash command that writes outside the project, to see whether the sandbox is on. The trials are: nothing set; `skillOverrides` set `"off"`; `Skill(<name>)` and `Skill(skill:<name>)` deny rules; `Agent(builder)` denied; `disableAllHooks: true`; the plugin set `false` in `enabledPlugins`; the sandbox on in the project's settings, alone and with a local `false`; `skillOverrides` and a deny rule in the committed settings for the personal skill; a route set, taken away and set again between three sessions; the same in the worktree; and the two fall-backs below.
- **The fall-backs, tried too.** The skill, agent and command moved out of the main checkout with their files marked `git update-index --skip-worktree`, then `git status` and `git add --all` read, and an `init` read in the main checkout and in the worktree; and the hook taken out of the main checkout's `.claude/settings.json`, marked skip-worktree, the same way.
- **Findings.** Every trial is kept in `trials.json` and the answers in `findings.json`, in the copies folder, and the answers are printed. A route counts only if it holds with both copies of Claude Code; where they differ, the findings say so. A kind's answer is left untried (`null`) unless the baseline, with nothing switched off, shows that part running. Otherwise each kind's `route` is a value Tasks 3, 5 and 7 read as it is: `{ route: 'setting', file, key, value }` (or `add`, for a list such as `permissions.deny`) with `typedRefused`, for the setting that held; `{ route: 'move' }` for a skill, agent or command no setting kept out, which takes the move below; or `{ route: 'none', instead }` for a hook or a personal skill, with `instead` saying what then. The agent's setting route also carries `blocksSameNamedPluginAgent`: `true` when the deny also stopped the plugin's `<plugin>:builder` on either copy, `false` when that ran on both, `null` when untried. A command counts as kept out only if Claude can't use it and, for `typedRefused`, the typed `/<name>` is refused, as for a skill. If an `init` event does not come with nothing sent, that copy goes straight to a short prompt for the rest of the run, and the findings say so.
- **Undo.** Uninstall, remove the marketplace, the scratch cache folder, the personal skill and the scratch folders, and compare the copied files. As in check 24, `~/.claude.json` is expected to differ in Claude Code's own state and is not copied back.

About 40 short sessions and 40 `init` reads in all, roughly 40 minutes on the Mac with nobody at it.

## Evidence

Nothing has been tried live. What the documentation says, untried:

- **Skill: `skillOverrides`, not a deny rule.** `"skillOverrides": { "<name>": "off" }` hides the skill from Claude and from the `/` menu; the documentation says that invoking a hidden skill by its full name "returns the `skillOverrides` error instead of running it", so a typed `/<name>` is expected to be refused. The key can be set in any settings file, and the `/skills` menu itself saves it to `.claude/settings.local.json`. It matches skill names only, and does not reach plugin skills. A `Skill(<name>)` deny rule is described as controlling which skills Claude can invoke; nothing says it refuses a typed `/<name>`, so it is expected to keep the skill from Claude only. Expected `route.skill`: `skillOverrides.<name>` = `"off"` in the local settings, with `/<name>` refused. Untried.
- **Command: the same as a skill.** "Custom commands have been merged into skills": `.claude/commands/<name>.md` makes `/<name>` and behaves as a skill named for its file. So the same `skillOverrides` entry is expected to cover it, though the documentation does not say so of command files in so many words. The live run tries both sides: Claude asked to use `probe-command`, and `/probe-command` typed. Untried.
- **Agent: an `Agent(<name>)` deny rule.** `"permissions": { "deny": ["Agent(<name>)"] }` stops Claude using the subagent named `<name>`, and a deny in any file wins over an allow in any other. Agents can't be typed as `/<name>`, so that question does not arise. Not documented: whether `Agent(builder)` also refuses a plugin's `<plugin>:builder`. Wheelhouse's own agents must keep working when the first version's are off, so the live run dispatches the plugin's scoped name under that rule, and `route.agent.blocksSameNamedPluginAgent` gives the answer. Where it is `true` (or `null`), the deny can't be used for a project agent whose name one of Wheelhouse's agents also uses (Wheelhouse ships `agents/builder.md`): Task 3 moves that agent instead, as if its route were `{ route: 'move' }`, and denies the rest. Expected `route.agent`: `permissions.deny` plus `Agent(<name>)` in the local settings. Untried.
- **Hook: no route.** The hooks documentation says: "There is no way to disable an individual hook while keeping it in the configuration." Hooks from every settings file add together, so a local file can't take away a project hook. `disableAllHooks: true` in the local settings would stop the project's hooks, but outside managed settings it also stops user, local and plugin hooks and the mods the director installed. That includes Wheelhouse's own hooks and mod, so it is no route. Expected `route.hook`: `none`. Untried.
- **Personal skill, from the committed settings.** `skillOverrides` can be set in the project's `.claude/settings.json` and is matched by skill name, so `"<name>": "off"` there is expected to hide a skill in `~/.claude/skills/` in this project only. Untried.
- **`pluginOff`: yes, expected.** The plugin loading documentation is explicit: a plugin's value comes from the highest file that names it, and "to opt out of a project-enabled plugin on your machine, set the id to `false` in `.claude/settings.local.json`". Untried.
- **`sandboxOff`: yes, expected.** `sandbox.enabled` can be set in any file and the local file sits above the project's. The exception is an admin-required sandbox: there a repository's `false` is ignored when the director's own `~/.claude/settings.json` sets `true`. Locked's computer-wide file makes the sandbox admin-required (check 12) without switching it on in user settings, so a local `false` is still expected to apply; switching back leaves Locked first anyway. The live run tries it with the project's settings as Wheelhouse writes them: `enabled: true` and `allowUnsandboxedCommands: false`. Untried.
- **`sameName`: `project`, expected.** A project's `.claude/agents/` (priority 3) wins over a plugin's `agents/` (priority 5), and a plugin agent also carries a scoped name, `<plugin>:<name>`. Untried.
- **`untrackedLoads`: yes, expected.** The skills documentation doesn't mention git. The worktrees documentation describes skills, agents and commands that are untracked "because your `.claude/skills` is gitignored" loading from the main checkout, which suggests that loading follows the folder, not git. Untried.
- **Next session: yes, expected.** Claude Code watches the settings files and the skill and agent folders and applies most changes even to a running session; a new session reads everything afresh. The live run tries only between sessions. Untried.
- **`initBeforeModel`: expected yes.** The `system/init` event is the first in the stream, after only plugin-install and hook events, and lists `skills`, `agents`, `slash_commands`, `plugins` and `plugin_errors`. Whether it comes when no message has been sent is untried; if not, the probe starts a session with a short prompt, stops it at the `init` event and reports `initBeforeModel` false.
- **Worktrees.** On the Mac, a session in a worktree reads `.claude/settings.local.json` from the main checkout's root (Claude Code 2.1.211 and later). On Windows the local file stays with the worktree, so a route written in the main checkout would not reach Wheelhouse's worktree sessions there. Plugins installed at project scope from the main checkout also load in its worktrees. A session started in a worktree from the Desktop app reads its project configuration from the main checkout's root instead. Untried.

## What it means for the design

Until the live run, these are expectations only; Tasks 3, 5 and 7 should be built against what `findings.json` says, not this list.

- **Expected routes** (all in the project's `.claude/settings.local.json`, keyed by each part's own name): skills and commands `skillOverrides.<name>` = `"off"`, with the typed `/<name>` refused; agents `permissions.deny` plus `Agent(<name>)`; hooks `none`. The personal skills a project switches off: `skillOverrides.<name>` = `"off"` in the project's committed settings. Plugins: `enabledPlugins[<id>]` = `false` in the local settings beats the project's `true`. The sandbox: a local `sandbox.enabled: false` beats the project's `true`.
- **Same names.** A bare-name dispatch is expected to reach the project's agent, so while the first version's `builder` is on, a Wheelhouse agent of that name is reached only by its scoped name. The install check (Task 7) should dispatch Wheelhouse's agents by their scoped names. Where the deny also blocks the plugin's agent (`blocksSameNamedPluginAgent` not `false`), any project agent whose name one of Wheelhouse's agents uses takes the move fall-back instead of the deny, so Wheelhouse's own agent of that name keeps working.
- **Windows needs Step 3.** If the local file stays with each worktree on Windows, the switch-off has to be written into every worktree Wheelhouse makes there too, or into the main checkout and read through; the Windows run settles it.

What the note will need to settle, from the brief's fall-backs, if the live answers differ:

- **If no local setting keeps a project skill or agent out,** the switch-off moves it instead, on this computer only: into `briefDir(folder)/off/`, with the move in the journal, so the working copy shows it deleted until switching back. That leaves an uncommitted change in the main checkout, which the switch-over's `.git/info/exclude` entry can't hide. So the note must say whether `git update-index --skip-worktree` keeps it out of the first version's commits and out of Wheelhouse's sessions; the findings then give that kind `{ route: 'move' }`, the brief records `route: 'move'`, and Task 3 tests both. The probe tries this: `git status` and `git add --all` after the move, and an `init` read in the main checkout and in a worktree. A worktree checks out the commit, not the main checkout's files, so the moved parts are expected to be back in every worktree.
- **The hook,** with no route expected: the probe also tries taking it out of the main checkout's `.claude/settings.json` and marking that file skip-worktree. Whether that is acceptable (it hides every later change to that file from git in the main checkout), or whether Wheelhouse lives with the first version's hooks until it is retired, is for the note to settle with the live result.
- **If a local `false` doesn't beat the project's `true`,** switching back writes the plugin's `false` and the sandbox's `false` into the director's user settings, scoped by `projectPath` where check 24's route allows, or else becomes the setup plan's uninstall, and Card 2's wording changes to say so.
