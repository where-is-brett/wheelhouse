# The core cut: build plan (7 November 2026)

> **For agentic workers:** this is the coordinating plan. Each part below is built in its own session, worktree, branch and pull request. Inside a part, use superpowers:writing-plans to turn the part's section into task-by-task steps, then superpowers:subagent-driven-development, then superpowers:verification-before-completion. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cut Wheelhouse back to its core as the approved design says: frame the parking, drop Matt Pocock's plugin, make the own engine the only engine (with crash resume and the update's move off Archon), lift out every parked piece, and bring the documents and the release up to date.

**Architecture:** Nine parts from section 8 of the design, with part 3 split in two (3A crash resume, 3B the move off Archon) so crash resume can start at once. Parts whose files are disjoint run side by side; parts that share files run one after another, each starting as soon as the one before it has its pull request open. No two sessions ever write the same file at the same time.

**Tech Stack:** Node.js scripts (ES modules), `node --test`, GitHub Actions CI, Claude Code plugin files.

**Spec:** `docs/specs/2026-11-07-core-cut-design.md` (approved 7 November 2026). Way of working: `docs/specs/2026-11-07-director-way-of-working-design.md` on branch `design/director-way-of-working`, sections 5 and 6.2.

## Global Constraints

- One branch and one pull request per part. Open the pull request; never merge it. The director merges.
- No AI attribution anywhere: no `Co-Authored-By`, no "Generated with", no model names, in commits, pull requests, code or documents.
- Two sessions never write the same file at the same time. A part touches only the files its section gives it; anything else it finds that needs changing goes in its pull request's "Left for later parts" list.
- British or Australian English. Dates as day month year (7 November 2026).
- Every file starts with a comment giving its repository-relative path (JSON exempt; after front matter where there is front matter).
- No words such as "enhanced", "improved" or "fixed" in names, comments or user-facing text.
- The director is "the director", they/them.
- Scripts and hooks in Node.js, so they run on macOS and Windows.
- Run the test files a part touches (`node --test <files>`); leave the whole suite to CI. A part that deletes a module also deletes its tests and runs `git grep` for every import of it.
- A change under `vscode/` or to the scripts the add-on carries changes the `.vsix` hash: run `node scripts/addon/hash.js --write` and commit the result (until part 6 removes the add-on).
- The repository is public: no records of Wheelhouse's own use, no details of the director's other projects.
- Decision line (way of working, section 5): the director decides product behaviour, algorithms, cost, schema and migrations, auth and security, public interfaces and formats, major dependencies, deleting or removing features beyond what the design already decided, and large rewrites. Everything the design already decided is decided. The part decides internal structure, tests, CI and tooling, and minor dependencies, and lists each such call under "Engineering calls" in its pull request.
- A director-level question goes to the coordinating session (not to the director) in the section 6.2 shape below, and the part carries on with the recommended option meanwhile:

```
Decision needed: <question>   (holds up: <what waits>)
<Why now>
A. <option>. <cost>. <undoable?>
B. ...
C. <option> (recommended). ...
Recommended because: <2-3 lines>
Meanwhile: <what agent does>
Reply A, B, C, "why", or your own words.
```

## Review Focus

1. **Old records with retired keys.** A project record or profile holding `engine: 'archon'`, `capRequests`, `blindCards`, `known:*` or `watcherShape: 2` must load, check and show settings without an error, and nothing may act on those values. Pinned in part 1's tests and in each lift-out part's tests for its own keys.
2. **A feature session that dies mid-step, more than once.** Resume must count across watcher restarts (the count lives on disk, not in memory), and the third death makes exactly one card, not one per tick. Pinned in part 3A.
3. **An update run while Archon work is in flight.** A run still going at the quiet point is cancelled with its worktree and branch kept and queued as "carry on from what's there"; an update run twice does not cancel or queue twice. Pinned in part 3B.
4. **A core import of a lifted-out module.** After each lift-out, nothing in `scripts/`, `hooks/`, `commands/`, `skills/` or `agents/` imports a deleted file, and the session-start hook still runs on a project set up before the cut. Pinned in each lift-out part by a grep step and the session-start hook's tests.
5. **A status line or plugin the director set themselves.** The update removes only Wheelhouse's own status line (`isOwnStatusLine`) and only the project-scope Pocock install; a user-scope install or the director's own status line is left. Pinned in parts 2 and 5.

**Why this order and not more side by side.** The design expected parts 2, 6 and 7 to touch separate files. They don't: parts 6 and 7 share fifteen source files (among them `scripts/host/helper.js`, `scripts/settings/catalogue.js`, `scripts/hooks/session-start.js` and `scripts/desk/views.js`), part 6 shares `lineage/manifest.json` with parts 2 and 3B, and part 5 shares files with parts 2, 3B, 6 and 7. Part 4 touches almost every area. So only parts 1, 2 and 3A run side by side, and the rest run in a chain.

**Branching.** Parts 1, 2 and 3A branch from `main`. A later part branches from `main` if every part before it in the table has merged; otherwise it branches from the branch of the part just before it (part 3B: from part 2's branch, then merges part 1's and part 3A's branches in), and its pull request's base is that branch, so the director sees only its own diff. When the part before merges, GitHub moves the base to `main` (branches are deleted on merge). Each pull request says which pull requests it stacks on.

**Merge order for the director:** 1, 2, 3A, 3B, 6, 7, 5, 8, 9; then the release (v0.3.0) is tagged and every project updated; then 4.

**Reading the plan and the design from a part.** Both live on branch `feature/core-cut-plan-f08509` until they merge:

```bash
git fetch origin
git show origin/feature/core-cut-plan-f08509:docs/superpowers/plans/2026-11-07-core-cut.md
git show origin/feature/core-cut-plan-f08509:docs/specs/2026-11-07-core-cut-design.md
```

**Every part's pull request** has: what it does in plain words (two or three lines), the design sections it builds, "Stacks on" (if any), "Engineering calls", "Left for later parts", and the tests run with their result.

## Part 1: The parking frame

**Design:** sections 4.1 and 8.1.

**Files (owned):**
- Create: `docs/parked.md`
- Modify: `scripts/settings/catalogue.js`, `scripts/settings/effective.js`
- Test: `tests/scripts/settings/catalogue.test.js`, `tests/scripts/settings/effective.test.js`
- Tags: `parked/<piece>`, listed below

**Not to touch:** anything else. Moving each piece's own keys into the retired list is the lift-out part's job, not this one.

**Interfaces (produces, used by parts 3B to 8):**
- `RETIRED` in `scripts/settings/catalogue.js`: a frozen object from a retired key to the name of the piece that retired it, for example `{ capRequests: 'copilot' }`. Starts empty.
- `RETIRED_PATTERNS`: a frozen array of `{ pattern: RegExp, piece: string }` for families of keys (part 7 adds `known:*`). Starts empty.
- `retiredPiece(key) -> string | undefined`: the piece a key was retired by, from either list.
- `definitionOf(key)` returns `{ label, group: 'retired', retired: true, piece, home: 'project' }` for a retired key; `checkSetting` and `isAllowed` accept any value for it, with or without `until`.
- Effective settings (`scripts/settings/effective.js`) never return a retired key, and any list of settings shown to the director leaves retired keys out.
- A lift-out part retires a key by deleting its `SETTINGS` entry and adding one line to `RETIRED` (or `RETIRED_PATTERNS`).

**Tags.** At the `main` commit this part branches from, where every piece is whole, create and push these lightweight tags: `parked/mod`, `parked/copilot` (with Lean), `parked/archon`, `parked/vscode-addon`, `parked/delegation` (with concept learning), `parked/screenshot-approvals`, `parked/windows-locked`, `parked/unattended-goals`, `parked/engine-side`. Pushing them is an engineering call to note in the pull request.

**`docs/parked.md`.** One entry per tag, each with: what it was (one or two lines), its tag, its designs and plans (paths under `docs/specs/` and `docs/superpowers/plans/`), why it was parked (from design sections 2.4, 4.2 and 4.3), what bringing it back would take (a short design against the core of that day, then a build from the tag; nothing switches itself back on), and the settings it retired (from the table in section 4.2). The Archon entry also carries the date to look again, 7 February 2027, and the four triggers from section 4.3.

**Tasks:**
- [ ] Tests first: a key put in `RETIRED` (tests inject one through a parameter or a test-only copy, not by changing the shipped list) is accepted with any value by `checkSetting` and `isAllowed`, is not "no setting called", has `definitionOf(key).retired === true`, and never appears in effective settings or the settings list; a key matching a `RETIRED_PATTERNS` entry behaves the same; an unknown key still throws `Wheelhouse has no setting called …`.
- [ ] Build the mechanism to pass them.
- [ ] Write `docs/parked.md`.
- [ ] Create and push the tags.
- [ ] Run `node --test tests/scripts/settings/`. Open the pull request.

**Done when:** the tests pass, `docs/parked.md` has an entry for every tag, the tags are on the remote, and the pull request is open.

**The move (section 6 item 1), in order:**
1. From the moment the update starts, the `engine` setting is read as `wheelhouse`: no new work goes to Archon.
2. Work under way on Archon is given until the next quiet point. A run still going then is cancelled through the connector, with its worktree and branch kept, and queued for the own engine as "Carry on from what's there." on the same branch (the existing Carry on route, the other way round).
3. An unanswered Archon question stays a waiting card, and its answer goes into the carried-on work's order.
4. Open pull requests stay open; the helper's gate merges them as usual.
5. Records of Archon's runs stay as they are.
6. `.archon/` and the merge queue's policy file are removed by one helper pull request, on the director's approval card.
7. Archon on the computer (the engine folder, the pinned Bun and Archon's database) moves to `~/.wheelhouse/archive/` once no project on the computer uses it; it is deleted only on the director's own later card.

Each step is listed on the Update card in plain words where it applies, and the update journal can undo it. An update run twice does not cancel or queue twice (Review Focus 3).

**Tasks:**
- [ ] Tests first for each step of the move, including the run-twice case; then build it.
- [ ] Setup without Archon, test first.
- [ ] No Archon upgrades: the pin, digests, patches and the upgrade leg go; Superpowers and Claude Code stay.
- [ ] Run the touched tests. Open the pull request.

**Done when:** a project on Archon moves to the own engine through the update in the tests, setup's tests pass without the engine step, the upgrade has no Archon leg, and the pull request is open.
